# Implementation Log: Model Verification and Phase 1 Infrastructure

*A step-by-step record of work completed so far, written for use as source material for the Methods/Implementation section of the research paper.*

---

## 1. Background

The study (full design in `Complete_Experimental_Design_LLM_Semgrep_MultiAgent.md`) benchmarks open-weight code LLMs on their ability to convert real vulnerability-fixing patches into executable Semgrep rules, using **Autogrep** as the common processing pipeline. Before any experiment could run, two things had to be settled: (1) which specific models are actually usable on the available infrastructure, and (2) a working, version-pinned copy of the Autogrep pipeline itself. This log covers both.

All model inference in this study runs on **GPT-Lab**, a GPU cluster exposing an OpenAI-compatible API across several hosts (`GPU-farmi-001` through `004`, `CSC-P100`, and others), each hosting a different subset of locally-pulled Ollama models.

### 2.2 Constraining to real, available infrastructure

Rather than assume these models' exact deployment names, the full GPT-Lab model catalog was inventoried first (123 distinct model IDs across 8 hosts, recorded in `Open Models/MODELS.md`). This mattered because a model name used in a paper or a Hugging Face model card does not always correspond one-to-one with the tag actually deployed on a given inference host — suffixes like `-instruct`, `-chat`, or `-it` are sometimes present, sometimes absent, and sometimes simply don't exist for a given model on a given platform.

### 2.3 Empirical instruction-tuning verification

Since Semgrep-rule generation is an instruction-following task, every candidate needed to be confirmed as genuinely instruction-tuned, not a base/completion model. Assuming this from the tag name alone was judged unreliable, so each candidate was tested directly against the live GPT-Lab endpoint using two probes:

1. **Strict-format probe:** "Respond with only the single word: DONE. Do not say anything else."
2. **Direct Q&A probe:** "What is the capital of France? Answer in one short sentence."

An instruction-tuned model follows the format and answers correctly; a base/completion model ignores the instruction and instead continues generating plausible-looking text (e.g., echoing the prompt or hallucinating further "prompts").

**Method:** each model was queried via HTTP POST to its host's `/v1/chat/completions` endpoint (OpenAI-compatible), at `temperature=0`, and the raw text response was inspected directly — no automated classifier, just visual inspection against the pass/fail criterion above.

## 3. Phase 1: Pipeline Infrastructure

### 3.1 Understanding the base tool (Autogrep)

Before writing any integration code, Autogrep's actual source (`github.com/lambdasec/autogrep`) was read in full to understand its real structure, rather than assuming one:

- It is a small set of flat Python scripts (no package structure): `main.py` (orchestrator), `config.py`, `llm_client.py`, `patch_processor.py`, `rule_validator.py`, `rule_filter.py`, `rule_manager.py`, `git_manager.py`, `cache_manager.py`.
- **`llm_client.py`** contains a single class with one method, `generate_rule()`, hardcoded to call OpenRouter's API with the model `deepseek/deepseek-chat`. This is the one place in the codebase that needs to be replaced to point the pipeline at GPT-Lab models instead.
- **`rule_validator.py`** validates a generated rule by invoking the Semgrep CLI as a subprocess against the vulnerable and patched versions of the affected file.
- **`rule_filter.py`** removes near-duplicate rules (via sentence-embedding similarity) and runs a second LLM pass that judges whether a rule is generalizable or overly specific to one repository.
- **`main.py`** finds patch files, groups them by repository, and retries generation up to a configurable limit, feeding the validator's error message back into the next generation attempt.
- The repository ships example *output* (`generated_rules/`, `filtered_rules/`) but no example *input* patches and no automated test suite.

### 3.2 Vendoring and pinning

- Cloned the repository into a local `autogrep/` directory and recorded the exact commit hash (`ace3c87a707a5b02632906b76195b6f97d411b8d`) in a `PINNED_COMMIT` file, so the exact version used in the study is reproducible.
- Cloned Autogrep's required initial rule set (`patched-codes/semgrep-rules`) into `autogrep/rules/`.

### 3.3 Environment setup

- Created an isolated Python virtual environment and installed Autogrep's declared dependencies (`gitpython`, `pyyaml`, `requests`, `semgrep`, `openai`, `sentence-transformers`).
- **Version discrepancy caught:** the system-wide Semgrep installation was version 1.140.0, but the version installed inside the project's virtual environment was 1.177.0 — a different version that will actually be invoked once the environment is activated. Both the discrepancy and the pinned version actually in use were recorded explicitly (`PINNED_VERSIONS.txt`), since an unrecorded version mismatch would undermine reproducibility.

### 3.4 Constructing a real end-to-end test case

Autogrep ships no example input patches, and downloading its full source dataset (MoreFixes, tens of thousands of patches) was judged premature for an infrastructure smoke test — that belongs to the later dataset-curation phase. Instead, one real test case was reverse-engineered from Autogrep's own example output:

1. Selected one of Autogrep's pre-generated example rules (`vuln-aiohttp-1c335944.yml`), which targets a real directory-traversal vulnerability (CWE-22) in the `aiohttp` Python library.
2. The rule's metadata pointed directly to the real GitHub fixing commit.
3. Downloaded that commit's actual diff from GitHub and saved it under Autogrep's required filename convention (`github.com_{owner}_{repo}_{commit-hash}.patch`), giving one genuine, verifiable test input without needing the full dataset.

### 3.5 Smoke test

Ran the vendored pipeline against this one real patch (using a placeholder API key, since the GPT-Lab model adapter has not been built yet — that is the next step). Results:

| Pipeline stage | Outcome |
|---|---|
| Repository cloning (`aio-libs/aiohttp`) | ✅ Succeeded |
| Commit resolution | ✅ Succeeded — correct commit found |
| Patch file parsing | ✅ Succeeded |
| Existing-rule pre-check (via real Semgrep execution) | ✅ Ran without error |
| Rule generation attempt reached | ✅ Reached — confirms the pipeline gets all the way to the LLM call |
| LLM call itself | ❌ Failed with 401 Unauthorized (expected — a placeholder key was used deliberately, since this study does not use OpenRouter) |

This confirms every stage of the pipeline works correctly against a real, verified vulnerability-fixing commit, up to (and stopping precisely at) the one call site that will be replaced with a GPT-Lab-backed adapter in the next implementation step.

## 4. Phase 1, Step 2: the GPT-Lab model adapter

### 4.1 Discovery: two hardcoded LLM call sites, not one

Reading the vendored source in full (rather than assuming a single seam) revealed that Autogrep calls an LLM in **two independent places**, both hardcoded to OpenRouter's `deepseek/deepseek-chat`:

1. `llm_client.py`'s `generate_rule()` — the main rule-generation call.
2. `rule_filter.py`'s `evaluate_rule_quality()` — a second, separate LLM call (with its own independently-constructed API client) that judges whether a generated rule is generalizable or too project-specific, used during the filtering/Autogrep-condition stage.

### 4.2 Design decision: extend, don't subclass

Rather than writing a new client class to sit alongside Autogrep's existing code, the two hardcoded literals in each call site (model name and, for generation, temperature) were replaced with values read from configuration, with the original hardcoded values kept as defaults — so nothing about Autogrep's original behavior changes unless the new configuration fields are explicitly set. This was a smaller, more maintainable change than duplicating Autogrep's prompt-construction and YAML-parsing logic in a separate adapter class, and it means both call sites can point at any GPT-Lab model without touching them again.

A small helper module (`pipeline/gptlab_config.py`) was added to:
- Map each verified model tag to the correct GPT-Lab host.
- Read the API key from an environment variable (`GPTLAB_API_KEY`) — never hardcoded in source, including fixing a pre-existing hardcoded key found earlier in `Open Models/models.py`.
- Build a ready-to-use configuration object for a given model in one call.

### 4.3 Design decision: a fixed, constant judge model

The generalizability-judging call (point 2 above) creates the same self-certification risk already identified in the research design for test-variant labeling: if a model's own instance judges its own generated rule's generalizability, a weaker model could be filtered more or less leniently for reasons unrelated to actual rule quality. To prevent this, the judge call is always pinned to one constant model (`qwen2.5-coder:32b`), never the model currently being evaluated — implemented as a fixed constant in `pipeline/gptlab_config.py` rather than left to whichever model happens to be running.

### 4.4 Verification

**Generation call site**, tested against two different models on two different hosts, using the same real aiohttp test case from Step 1:

| Model | Host | Result |
|---|---|---|
| `qwen2.5-coder:7b-instruct` | GPU-farmi-001 | ✅ Generated a well-formed, Semgrep-validated rule correctly capturing the directory-traversal mechanism (symlink handling), with proper CWE/OWASP metadata |
| `deepseek-coder:6.7b` | GPU-farmi-004 | Connected correctly (confirmed via successful HTTP 200 responses on the right host) but failed to produce valid YAML across all 3 retry attempts — a genuine model-quality difference, not an adapter fault, and exactly the kind of outcome the study is designed to measure (syntactic validity varies by model) |

This also confirmed the retry limit is correctly respected: exactly 3 attempts were made for the failing case, matching the research design's configured value rather than Autogrep's own unconfigured default of 8.

**Judge call site**, tested by feeding the successfully-generated aiohttp rule back through `evaluate_rule_quality()` using the fixed judge model:

- Correctly connected to `qwen2.5-coder:32b` on its designated host.
- Returned a coherent decision (`REJECT`) with a substantive reason ("the rule uses project-specific code in the pattern-not section..."), confirming the judge call is functioning and producing sensible output, not just returning without error.

### 4.5 Two pre-existing Autogrep bugs noted (not yet fixed)

Neither affects correctness of the results already gathered, but both are worth revisiting before the full-scale benchmark:

1. In `main.py`'s `run()` method, a rule that was already saved once (inside `_process_repo_patches()`) is redundantly passed to `add_generated_rule()` a second time using `rule["language"]` — a key that does not exist on the rule dict, causing a caught-and-logged `KeyError`. Harmless (the rule is already saved correctly by the first call) but noisy in the logs.
2. Malformed model output that happens to parse as a YAML string rather than a mapping can trigger `'str' object does not support item assignment` inside the sanitization step. Currently just logged and treated as a failed attempt (correct behavior), but worth checking whether this occurs disproportionately for any specific model, which would need to be distinguished from genuine syntactic-invalidity in the final results.

### 4.6 One scaling note for later

The verification script gives each model its own repository-cache directory. Autogrep couples "which repos are cloned" and "which patches have already been processed" in the same cache directory — sharing one cache directory across models would cause the second model evaluated to silently skip any patch the first model already succeeded on. Fine for a one-patch smoke test; needs a real decision (e.g., a separate processed-patch tracker per model) before the full 300-case, 8-model benchmark in Phase 5.

## 5. Phase 1, Step 3: raw-output capture

### 5.1 Why this needed its own mechanism

The design (Section 15) distinguishes two conditions per generation: the **raw** condition (the model's first, untouched output) and the **Autogrep condition** (the final output after retry, validation, and filtering). Autogrep's own code does not preserve this distinction — its retry loop simply overwrites each attempt with the next one and returns only the final result (or nothing), with no record of what the very first attempt actually looked like.

### 5.2 Approach: wrap the API client, not the parsing logic

Rather than editing Autogrep's `generate_rule()` method (which builds the prompt, calls the API, then immediately strips markdown fences, re-serializes the YAML, and fills in missing fields, all in one method body), the raw-output capture wraps the *API client object* itself at the exact point Autogrep calls it (`self.client.chat.completions.create(...)`). This records the literal text the model returned before any of Autogrep's own cleanup runs — with no changes needed to Autogrep's parsing logic at all.

Each case's first captured call is written to a `raw/` directory and tagged as the raw condition; any further calls from the same case's retry loop are written separately to a `raw_retries/` directory, so they're preserved for diagnostic purposes (useful later for the Repair Recovery Rate metric) without contaminating what counts as "raw."

### 5.3 A side benefit: cases are now processed one at a time

Capturing raw output correctly requires knowing which case is currently being processed (to tag each captured call with the right case ID), which meant switching from Autogrep's bulk/threaded `run()` method to processing one patch at a time directly. This turned out to also sidestep the redundant-save bug found in Step 2 (Section 4.5, point 1) entirely, since that bug lived inside `run()`'s own loop, which is no longer used.

### 5.4 Verification

Re-ran both models from Step 2's test with raw capture wired in:

- **`qwen2.5-coder:7b-instruct`** (successful case): the captured raw file shows the model's actual response still wrapped in `` ```yaml `` markdown fences — direct, concrete evidence that raw capture records the genuinely untouched output, since those fences are exactly what Autogrep's cleanup step strips out before producing the final saved rule.
- **`deepseek-coder:6.7b`** (failing case, 3 attempts): produced exactly one file in `raw/` (attempt 1) and two files in `raw_retries/` (attempts 2 and 3) — confirming the first-attempt/retry distinction is tagged correctly, matching the real number of attempts observed in the logs.

## 6. Phase 1, Step 4: retry/config verification

### 6.1 What was already correct

`max_retries` and the generation `temperature` were already being pinned correctly throughout Steps 2–3 (3 and 0.0 respectively), never relying on Autogrep's own unconfigured defaults (8 and 0.6). This was re-confirmed directly rather than assumed.

### 6.2 A more significant finding: `max_files_changed` is not actually enforced

Checking where `max_files_changed` is used in the codebase (beyond just being stored) turned up nothing — it is read from the CLI/config but never compared against how many files a patch actually touches anywhere in the pipeline. This was confirmed empirically, not just by reading the code: the test patch used throughout Steps 1–3 touches two files with recognized languages (`aiohttp/web_urldispatcher.py` and `tests/test_web_urldispatcher.py`, both Python), `max_files_changed` was set to 1 the entire time, and the patch was processed successfully regardless — no rejection occurred.

**Implication for the study:** the design's "prefer one-file security fixes" requirement (Section 7.1) cannot be satisfied by trusting Autogrep's `--max-files-changed` flag — it does nothing. This constraint has to be enforced during dataset curation itself (Phase 2/4), by checking each candidate CVE case's file count directly before it's added to the benchmark set, not by relying on the pipeline to filter it at run time.

### 6.3 Confirmed already-fixed values (no change needed)

- The rule-filtering step's embedding model (`all-MiniLM-L6-v2`) and its duplicate-similarity threshold (0.9 cosine similarity) are already fixed constants — the threshold isn't even exposed as a command-line option, so there's no risk of it varying between runs.

### 6.4 Consolidated reference

All pinned values gathered across Steps 1–4 (software versions, generation parameters, filtering parameters, and the `max_files_changed` gap) are now recorded in one place: `pipeline/PINNED_CONFIG.md`.

## 7. Phase 1, Step 5: the result-record schema

### 7.1 Two record types, not one

The design's metrics (Section 21 — SCR, PDS, MCC, VGR, FPR, BSDR, ESR, ...) operate at different levels of granularity, so a single flat "one row per generation" record cannot hold all of them coherently. Two separate record types were defined instead:

- **`GenerationRecord`** — one row per (case, model, condition, attempt): what the model produced and whether it was executable at all. This is the direct output of Steps 2–4's pipeline.
- **`SampleExecutionRecord`** — one row per (case, model, condition, *sample*): whether one specific labeled test-bundle sample (original vulnerable, original patched, a transformed variant, a safe rewrite, a benign look-alike) was flagged. A single generated rule is tested against every sample in its bundle, so confusion-matrix outcomes (TP/FP/FN/TN) are inherently per-sample — not something a single generation event has one value for. Case-level metrics like PDS, VGR, and MCC are aggregates computed downstream from several of these rows, not fields stored on any one row.

The schema also directly encodes the design's finding-location-correctness rule (Section 9.3): a positive sample only counts as a true positive if the reported finding actually falls within the known vulnerable region — not merely anywhere in the file.

### 7.2 Verification against real data, not placeholders

Rather than testing the schema with made-up values, it was verified using the actual outputs already produced in Steps 2–3:

- Re-executed the already-generated `qwen2.5-coder:7b-instruct` rule against the real checked-out vulnerable and patched commits, reusing Autogrep's own `RuleValidator._run_semgrep()` (rather than reimplementing Semgrep invocation) to get genuine finding data, including real line numbers.
- The rule's finding landed at line 577 — which falls inside the actual changed-line range (573–581) taken directly from the patch's diff hunk header — confirming the location-correctness check works correctly on real output, not just in the abstract. (It also matched a second, unrelated location elsewhere in the file, line 643 — this doesn't affect the outcome here since at least one correct-location match is sufficient for a true positive, but it's a concrete illustration of exactly the "a report elsewhere in the file" scenario Section 9.3 is designed to guard against.)
- Built one `GenerationRecord` for the successful case and one for the `deepseek-coder:6.7b` failure case from Step 3, and two `SampleExecutionRecord`s (original vulnerable, original patched) for the successful rule.
- All records were written to JSONL, read back, and confirmed identical — a clean round trip.
- The aggregation helpers correctly derived: confusion counts `{TP: 1, FP: 0, FN: 0, TN: 1}`, a patch-discrimination hit of `True`, and `MCC = 1.0` — all matching what should follow from one correct detection and one correct non-detection. `VGR` correctly returned `None`, since no transformed variants exist yet (that's dataset-curation work, Phase 2/4, not part of Phase 1 infrastructure).

## 8. Phase 1, Step 6: the orchestration entry point

### 8.1 Bringing Steps 1–5 together

`pipeline/run_generation.py` is the script that actually runs the benchmark: given one or more model tags and a directory of `.patch` cases, it processes every case through both conditions and writes structured JSONL logs plus a per-run environment record. It is built entirely on what the previous five steps already established — the GPT-Lab adapter, raw capture, the result schema, and the pinned configuration — rather than introducing a new mechanism.

### 8.2 One necessary refactor: separating "what the model said" from "what Autogrep decided to do with it"

Correctly implementing the raw-vs-Autogrep-condition distinction (Section 15) required being able to independently re-evaluate attempt 1's captured output on its own terms — not just trust whatever Autogrep's live retry loop happened to do with it. `llm_client.py`'s `generate_rule()` bundled API-calling and response-parsing together in one method, so a small, behavior-preserving refactor extracted the parsing/sanitizing logic into its own method (`parse_and_sanitize_response()`). The live generation path calls it exactly as before; the orchestrator additionally calls it directly on the raw-captured text, independent of the live retry loop, to score the raw condition on its own merits.

### 8.3 A second reusable module: sample evaluation

`pipeline/sample_evaluation.py` factors out "run this rule against the vulnerable and patched version of every file in the case" (Section 16.2, Stage B) into its own function, reusing `RuleValidator._run_semgrep()` rather than duplicating Semgrep invocation. It also parses the changed-line ranges directly from each patch's own diff hunk headers, so the finding-location-correctness check (Section 9.3) runs automatically for every case — no per-case metadata needs to be supplied by hand, closing a gap that Step 5's verification had only checked manually.

### 8.4 Verification

Ran the complete orchestrator, from a clean results directory, against both models used throughout Phase 1:

- **`qwen2.5-coder:7b-instruct`**: both the raw and Autogrep condition records correctly show a valid, Semgrep-passing rule (identical outcome for both, since generation succeeded on the first attempt); both conditions' sample records correctly show TP for the original vulnerable sample and TN for the original patched sample; `finding_location_correct` is automatically `true`, derived from the patch's own diff hunk (line 577 falls inside the automatically-parsed range 573–581) — matching Step 5's manually-checked result exactly, but now fully automatic.
- **`deepseek-coder:6.7b`**: both conditions correctly show `yaml_valid: false` with no rule produced, and correctly produced zero sample-execution records (there is no rule to test against samples) — the empty result here is the correct behavior, not a bug.
- `environment.json` correctly captured the model, host, Semgrep version (1.177.0), and the pinned Autogrep commit hash alongside the results, satisfying Section 13.5.

### 8.5 What's still out of scope, by design

Transformed-variant and benign-lookalike samples are not evaluated yet, because they don't exist — building the labeled six-sample test bundle is dataset-curation work (Phase 2/4), not infrastructure. The orchestrator is written to pick these up automatically once they exist (it iterates whatever files a case has, rather than assuming exactly two), so no further pipeline changes should be needed when that data arrives.

## 10. Before Phase 2: implementing both candidate prompts

Every test so far had used Autogrep's own built-in prompt unmodified. The design doc's Section 13.2 specifies a different, shorter template, and explicitly calls for the prompt to be *developed* using pilot cases — implying both should be real, testable options rather than a choice made on paper before any pilot data exists.

### 10.1 What was built

- `Config.prompt_variant` (`"autogrep_default"` or `"design_v1"`), threaded through `pipeline/gptlab_config.py` and exposed as `--prompt-variant` on `run_generation.py`.
- `llm_client.py`'s prompt-building was split into `_build_prompt_autogrep_default()` (the original, untouched) and a new `_build_prompt_design_v1()` implementing the design doc's template, reconstructing "Vulnerable code" / "Patched code" as two separate clean blocks from the diff's `-`/`+` lines (rather than one interleaved diff) — directly targeting the diff-side-confusion failure mode documented in `Model_Failure_Root_Cause_Analysis.md`.
- The exact rendered prompt is now captured alongside every raw generation (via `raw_capture.py`), and hashed into `GenerationRecord.prompt_hash` — closing a previously-unused schema field and satisfying the design's Section 26 reproducibility requirement for prompt hashes.

**Provisional, by necessity:** `design_v1`'s CVE/CWE fields are placeholders (`"unknown"`) for now, since `PatchInfo` carries no case metadata yet — that only exists once Phase 2 curation produces real case manifests (Section 10's schema). The vulnerable/patched code blocks are also diff-derived, not the complete function body Section 8 ultimately calls for. Both should be revisited once real curated cases exist.

### 10.2 Two real bugs found while testing design_v1, both fixed

1. **Diff-header leakage**: a unified diff's own `--- a/file` / `+++ b/file` header lines start with `-`/`+` just like real content lines. The first version of the vulnerable/patched split included them verbatim, leaking `-- a/aiohttp/web_urldispatcher.py`-style garbage into the "Vulnerable code" block. Fixed by explicitly excluding `---`/`+++` lines before splitting.
2. **Schema-validation failures weren't fed back specifically on retries**: regardless of which prompt was used, when a rule failed schema validation (e.g. an invalid severity value), Autogrep's retry loop only passed a generic `"Failed to generate valid rule structure"` message into the next attempt — never the actual reason. Only Semgrep-validation failures got specific feedback. Fixed by adding `LLMClient.last_error`, set at every failure point inside `parse_and_sanitize_response()`/`generate_rule()` and cleared on success, which `main.py`'s retry loop now reads instead of always falling back to the generic message.

### 10.3 One genuine finding about the design doc itself, resolved with the user

`design_v1`'s prompt template, taken literally from Section 13.2, requires a `severity` field but never states its valid values (unlike Autogrep's own prompt, which explicitly lists `ERROR, WARNING, INFO`). This reproduced identically across all 3 attempts on the pilot test case (`severity: HIGH`, rejected by schema validation every time) — not a fluke. Resolved by adding the explicit enum to `design_v1`'s prompt text, since this is exactly the kind of refinement Section 13.2 invites ("develop the prompt using pilot cases"), and it keeps the eventual comparison focused on the real difference under test (separated code blocks vs. interleaved diff) rather than an incidental formatting gap.

### 10.4 Verification

After both fixes: `design_v1` against `qwen2.5-coder:7b-instruct` correctly progressed past schema validation to Semgrep validation on every attempt (severity issue resolved), and correctly surfaced a real Semgrep rule-parse error (lowercase `$cond` metavariable) via the fix from Section 8 rather than silently masking it — confirming that fix generalizes beyond the one case it was originally found on. The model did not self-correct this specific mistake across 3 attempts despite receiving the exact error text each time — a genuine model-behavior data point, not a bug.

### 12.3 A more significant finding: two mislabeled ground-truth samples

With generation now succeeding, the full six-sample bundle evaluation surfaced something worth taking seriously: `CASE-0009`'s `benign_lookalike.py` (labeled safe/negative) was flagged as detected by a rule that should only match the real, unfixed vulnerability — an unexpected result worth chasing rather than shrugging off.

Traced it to the file itself: line 239 of `benign_lookalike.py` still contained the literal unfixed vulnerable line (`raise EOFError(read_bytes)`), not the safe rewritten message `variant_safe_01.py` has. The corresponding `build_bundle_case0009.py` script (written during today's earlier Section 9 work) built `benign_lookalike.py` from `original.replace(...)` instead of `safe_source.replace(...)` — a copy-paste-style variable-name slip that the file's own syntax check couldn't catch (both produce valid Python; only the *content*, not the structure, was wrong), and that the transformation manifest's own `"base_file": "vulnerable_source.py"` field had been faithfully (if unhelpfully) recording all along without it being read as a red flag.

**Checked whether this was isolated or systemic** rather than assuming either way: every one of the 40 cases' manifest entries for `benign_lookalike` says `"base_file": "vulnerable_source.py"` — so that field alone doesn't distinguish a real bug from normal (if confusingly-labeled) provenance tracking. Went to the actual construction code instead: grepped all 40 `build_bundle_case*.py` scripts for how each one builds `benign_source`. Exactly two — `CASE-0001` and `CASE-0009` — used `original.replace(...)`; the other 38 correctly used `safe_source.replace(...)` (or equivalent, e.g. `SAFE_SOURCE + ...` for scripts using different variable-naming conventions). Confirmed the three ambiguous-looking grep misses (`CASE-0002`, `CASE-0008`, `CASE-0020`) by hand — all three were correct, just phrased differently syntactically.

**Fixed both scripts** (changed `original` → `safe_source`, and added an explicit assertion — e.g. `assert "raise EOFError(read_bytes)" not in benign_source` — so a future re-run of either script would fail loudly instead of silently regressing), regenerated both `benign_lookalike.py` files, and reverified: neither now contains its case's real vulnerable line.

**Then swept all 40 cases for the same class of mistake**, not just these two symptoms. A first attempt (checking whether `benign_lookalike` contains `variant_safe_01`'s full text as a contiguous substring) produced 38 false positives — wrong test, not wrong data: most construction scripts *insert* the new method into the middle of `safe_source` rather than appending it, which breaks simple substring containment even when the construction is completely correct. Replaced it with a more targeted diff-based check: for each case, compute the lines present in `vulnerable_source` but removed/changed in `variant_safe_01` (the vulnerability-specific content the real fix touched), then check whether any of those specific lines survive into `benign_lookalike`. This flagged 8 cases; each was individually verified by hand rather than trusted on the heuristic's say-so:
- Four (`CASE-0016`, `CASE-0022`, `CASE-0027`, `CASE-0034`) were already-known, deliberately-documented cases where a *second, out-of-scope sibling occurrence* of the same textual pattern exists elsewhere in the same file (untouched by the real patch and explicitly noted as such in that case's own transformation-manifest entry from Section 9) — expected, not a bug.
- Four (`CASE-0002`, `CASE-0003`, `CASE-0005`, `CASE-0012`) were coincidental matches on short, common boilerplate lines (an import statement, a bare `return null;`, a loop condition that also appears verbatim inside the safe rewrite's own logic) — confirmed safe by reading each file directly and checking for the case's actual vulnerable marker (e.g. `eval(request.operation)` for `CASE-0002`), which was absent in all four.

No further genuine defects found. ### 12.4 Reliability and throughput fixes, applied without disturbing the live pilot screening run

The full pilot screening (40 cases × 8 primary models × 2 prompt variants) was launched as a long-running background process. While it was in progress (design_v1 phase, several models still pending), monitoring surfaced two further real defects and two structural limitations, none blocking the run's eventual completion but all worth fixing before any larger (e.g. 300-case final) run:

- **Metadata-as-list `TypeError`** (already root-caused earlier, fix deferred at the time per explicit instruction): `_sanitize_rule()` assumed `rule['metadata']` was always a dict once present; `codellama:7b-instruct-fp16` occasionally returns `metadata:` as a YAML list, crashing `metadata['source-url'] = ...` with `TypeError: list indices must be integers or slices, not str` and silently dropping 4 of that model's 40 cases (CASE-0005, CASE-0025, CASE-0030, CASE-0031) even though the run otherwise looked complete. Fixed by coercing any non-dict `metadata` to a fresh `{}` before use, same principle as the earlier id-sanitization fix. Verified in isolation (no live API calls): a rule with `metadata` as a list of single-key mappings is now correctly coerced rather than crashing.
- **`RecursionError` on pathological YAML**: `yaml.safe_load()` can exceed Python's default recursion limit on deeply-nested generated YAML (observed live on CASE-0008 / `deepseek-coder:6.7b`). Previously uncaught inside `clean_yaml_text()`/`parse_and_sanitize_response()`, so it propagated past the per-case `try/except` in `run_generation.py` and the case vanished from the log entirely — no `GenerationRecord` at all, not even a failure one. Now caught alongside `yaml.YAMLError` at both sites, so it resolves to a normal `None` return with `last_error` set, flows through Autogrep's ordinary retry loop, and produces a real failure record like any other malformed response. Verified in isolation with a 5000-level synthetic nested-YAML string: no crash, clean `None` + descriptive `last_error`.
- **No per-call timeout**: the `OpenAI` client had no timeout configured, so a stalled GPT-Lab host could block the entire sequential run indefinitely — observed twice as ~10-20 minute stalls on `deepseek-coder:6.7b` (GPU-farmi-004). Added `Config.request_timeout_seconds` (default 120s, generous relative to normal observed call latency of single-digit-to-low-tens of seconds even for the 32b model) and passed it to the `OpenAI(...)` client constructor. A timed-out call now raises inside `generate_rule()`'s existing `except Exception` handler like any other API error, rather than hanging.
- **No resume/checkpoint support**: restarting `run_generation.py` after an interruption re-ran every case from scratch, re-billing GPU time for already-complete work. Added `_completed_case_ids()`, which reads a run's `generation_log.jsonl` and returns case IDs that already have both `raw` and `autogrep` condition records logged; both `run_model_on_cases()` and `run_model()` now skip those on start. Verified in isolation against a synthetic log with one deliberately-interrupted case (only `raw` logged, no `autogrep`) — correctly excluded from "complete" and left to be redone.
- **Fully sequential across models**: all 8 primary models ran one at a time regardless of GPU host, even though they're served by 3 distinct hosts (`GPU-farmi-001`, `-003`, `-004`). Restructured `run_generation.py`'s `main()` to group models by host (`MODEL_HOSTS`) and run each host's group on its own thread via `ThreadPoolExecutor`, so distinct hosts execute concurrently while models sharing a host stay sequential against it (avoiding *more* contention on an already-contended host). Required removing a module-level mutable global (`_CASE_FROZEN_MANIFEST`) that `evaluate_case_from_curated()` read from, since concurrent threads writing/reading a shared global is a race even when the values happen to coincide — replaced with an explicit `frozen_manifest` parameter threaded through both functions. Confirmed no other shared mutable state exists across `AutoGrep`/`RuleManager`/`CacheManager` that would make per-thread instances unsafe (each thread's `Config` points at a distinct `run_dir`/`repos_cache_dir`; `RuleManager.rules` is per-instance; no `os.chdir`/global env mutation anywhere in the vendored code).
  - **Caveat worth recording accurately rather than glossing over**: host distribution is lopsided — 5 of the 8 primary models (`qwen2.5-coder:32b`, `deepseek-coder:6.7b`, `codegemma:7b`, `yi-coder:9b`, `DeepHat/DeepHat-V1-7B`) all share `GPU-farmi-004`, with only `GPU-farmi-001` (2 models) and `GPU-farmi-003` (1 model) as the other lanes. Best-case speedup from host-level parallelism alone is therefore roughly 8/5 ≈ 1.6×, not the 3-4× a naive "3 hosts, so 3× faster" estimate would suggest, since the `-004` lane still processes 5 models sequentially and dominates total wall-clock time.

All four fixes were made to files the **already-running background pilot screening process (PID 20611, `design_v1` phase)** does not re-read — Python does not hot-reload source after a module is imported, so editing these files on disk while that process keeps running does not affect it. Per explicit instruction, that process was left completely undisturbed; every fix above was validated through isolated unit checks (no live GPT-Lab API calls, so as not to add load to hosts the live run was actively using) rather than by restarting or duplicating the run. The fixes take effect automatically on the run's own not-yet-started `autogrep_default` phase (a fresh `python pipeline/run_generation.py` invocation, which imports current-on-disk code) and on any future manually-started run (e.g. a resumed/completed pilot screening, or the eventual 300-case final run).

### 12.5 Pilot screening completes; two more real bugs found closing out the last few cases

The full pilot screening run finished on its own ("=== PILOT SCREENING RUN COMPLETE ===") after roughly 19.5 hours. Per-model completeness was checked properly this time — a case only counts as done once it has BOTH a `raw` and an `autogrep` condition `GenerationRecord`, not just any record at all (an earlier, looser check that only looked for the case_id appearing anywhere had been silently over-counting). That check found 8 genuinely incomplete cases spread across three models (`codellama:7b-instruct-fp16`, `deepseek-coder:6.7b`, `magicoder:7b`), matching the bugs already diagnosed and fixed in Section 12.4.

Re-running `run_generation.py` for just those (model, prompt) pairs did nothing at first — Autogrep has its OWN persistent cache, independent of this project's new resume logic: `CacheManager.is_patch_processed()` (`autogrep/cache_manager.py`), backed by a `processed_patches.json` file under each run's `cache/repos/` directory, marks a patch filename as processed the first time it's attempted regardless of success or failure (`autogrep/main.py` lines 37-44), and since the pipeline reuses a stable per-case synthetic patch filename across invocations, Autogrep silently short-circuited every retry with "Skipping already processed patch" and returned `None` without ever calling the LLM again. Fixed operationally, not by changing code: removed just the specific stuck patch filenames from each affected run's `processed_patches.json` (not the whole cache — repo clones cached alongside it are unaffected and expensive to redo) before each backfill attempt.

Backfilling then surfaced a second new bug, this time in `_sanitize_rule()`'s rule-unwrapping step (`rule = rule['rules'][0]`), traced with a full traceback reproduced directly against the real captured raw content (CASE-0030 / `codellama:7b-instruct-fp16`, attempt 2): `TypeError: 'str' object does not support item assignment` on the very next line (`rule['id'] = ...`). Root cause: `clean_yaml_text()`'s salvage path (triggered when the model's YAML doesn't parse cleanly the first time) can produce a `rules:` list whose first element is a bare scalar string rather than a nested mapping — in this real case, the model's response opened with a fence containing a stray label line (a bare code fence, then a line reading just "YAML", then the actual rule fields), and that stray "YAML" line parsed as `rules: ["YAML"]` while every real field (id, pattern, message, severity, metadata, ...) ended up as SIBLING top-level keys next to `rules`, not inside it. The old code unconditionally replaced `rule` with `rule['rules'][0]` (the string "YAML"), discarding a dict that already had every required field, and then crashed trying to write into that string. Fixed by only doing the replacement when the candidate is actually a dict (`isinstance(candidate, dict)`); otherwise the original outer dict — which, as traced, already carries the real fields as siblings — is kept as-is. Verified against all 3 real captured attempts for this case: attempt 1 and attempt 2 (previously the crash) now both parse to a usable rule; attempt 3 (genuinely malformed) fails cleanly with `last_error` set instead of crashing. All existing tests re-run clean after this fix too.

Backfilling was done with the internal Autogrep-level `run_id` isolation in mind: each invocation of `run_model_on_cases()` generates a fresh `run_id`/raw-capture subdirectory, so re-running only regenerates the specific missing cases (thanks to this project's own resume logic skipping everything else) while writing NEW raw-capture files alongside the old ones rather than overwriting them — nothing already-complete was touched or reprocessed.

### 12.6 Offline re-scoring: a third finding, this one in the original extraction logic itself

While reviewing the completed pilot screening's results, `deepseek-coder:6.7b` and `magicoder:7b` stood out with an exact 0% yaml-valid rate under `autogrep_default` — every other model scored well above 0%. Comparing their raw captured output directly against a high-scoring model (`qwen2.5-coder:32b`) found the cause: those two models wrap their YAML in explanatory prose before and/or after the code fence ("Here is a basic example of how you could write a Semgrep rule..." ... the YAML fence ... "This rule will match..."), while `qwen2.5-coder` returns bare, unwrapped YAML. `extract_response()` only stripped the fence marker LINES themselves, never the prose surrounding them, so the leftover sentences broke `yaml.safe_load()` on effectively every generation for these two models — a parsing bug, not necessarily a sign of weaker rule-writing ability. Fixed by extracting the CONTENT of the first fenced code block when a fence is present, discarding anything outside it, falling back to the old marker-stripping behavior only when no closed fence exists at all (unfenced/truncated responses). Verified directly against both models' real captured CASE-0001 responses (previously unparseable, now both parse to a valid rule) and against three already-working models' responses (unaffected, still parse identically).

Because every raw model response across the whole pilot screening was already captured to disk (`raw_capture/*.json` per run), this fix — and the two from Section 12.5 — could be, and were, re-scored entirely offline: re-parsing captured raw text with the fixed `extract_response()`/`_sanitize_rule()`, then re-running the Section 9 six-sample bundle evaluation with `semgrep` locally (subprocess, no network) via `evaluate_case_bundle()`. No new GPT-Lab API calls were needed for this re-scoring pass.

**Correction to that offline re-scoring pass, caught before trusting it**: the first version approximated the "autogrep condition" (tool-assisted, retry-loop) score by taking whichever of a case's captured attempts (1/2/3) was the first to merely *parse*. That is not what the real retry loop does — `AutoGrep.process_patch()` (`autogrep/main.py`) only accepts an attempt once `rule_validator.validate_rule()` confirms it actually detects the vulnerable sample and stays silent on the patched one; a syntactically valid rule that fails that check is discarded and retried with error feedback, same as an unparseable one. Approximating "accepted" as "parses" understates real retry-loop quality, since it can settle for the first parseable-but-wrong attempt instead of the actually-correct one an error-feedback retry would have produced. Caught by comparing the offline pass's numbers against the original live run's already-recorded results for models that had good coverage (`qwen2.5-coder`, `codegemma`, `yi-coder`, `DeepHat`) -- the offline "autogrep" numbers were implausibly lower than the live run's own recorded numbers for the same models, which was the signal something in the offline approximation, not the live data, was wrong.

Resolution: the offline pass's "raw condition" numbers stayed valid (raw is exactly attempt 1, no retry semantics to approximate) and were kept. For the "autogrep condition," rather than build a better offline approximation, `deepseek-coder:6.7b` and `magicoder:7b` (the two models whose live `autogrep_default` results were entirely zeroed out by the original extraction bug) were **fully re-run live**, both prompts, all 40 cases, through the real, now-fixed pipeline -- into a separate `results/runs_pilot_rerun_fixed/` directory so this project's own resume logic (which only checks for existing log entries, not their correctness) wouldn't skip them. One case (`CASE-0007`, `deepseek-coder:6.7b` × `design_v1`) failed identically on both this run and the earlier backfill attempt, each time with ~6-minute per-attempt stalls against GPU-farmi-004 before timing out -- reproducible enough to treat as a genuine, documented single-case gap rather than a further code bug, and left as a real recorded failure (all three attempts logged, no raw capture) rather than retried a third time.

A second, smaller data-hygiene issue surfaced while assembling final numbers: `codellama:7b-instruct-fp16`'s `design_v1` run showed 44 "autogrep condition" records instead of 40, because the repeated backfill attempts in Section 12.5 (before the cache-skip and crash bugs were both fixed) had left stale failure records alongside the eventual real success for the same case IDs. Fixed by deduplicating `generation_log.jsonl`/`sample_execution_log.jsonl` to the latest record per `(case_id, condition)` before aggregating -- not by editing the log files themselves, which stay as the true append-only record of every attempt made.

**Final, trustworthy pilot-screening result** (all 8 models, both prompts, "autogrep condition," MCC as the headline metric per Section 21.9): `qwen2.5-coder:7b-instruct` ranks first overall (mean MCC 0.598 across both prompts), narrowly ahead of `qwen2.5-coder:32b` (0.567) -- notably, the smaller model in this family slightly outperforms the larger one on this task. `magicoder:7b` ranks clearly last (mean MCC 0.224), dragged down almost entirely by a near-total failure specifically under `design_v1` (MCC 0.0, 0/40 cases even parsing) despite performing reasonably under `autogrep_default` (MCC 0.447) -- a real, model-and-prompt-specific interaction, not a residual pipeline bug (both prompts now run through the same fixed extraction/sanitization code). Averaged across all 8 models, `autogrep_default` (mean MCC 0.541) clearly outperforms `design_v1` (mean MCC 0.394) as a prompt -- the older, longer, example-laden built-in Autogrep prompt beats the shorter, research-doc-specified template on this pilot, even though `design_v1` tends to produce a *higher raw YAML-validity rate* per Section 12.6's raw-condition numbers. Both observations (best model, best prompt) are pilot-only findings for selecting the final prompt and are not the study's locked, final result -- that comes from Phase 5's 300-case primary benchmark (Section 29).

**A finding worth stating as plainly as the ranking itself: absolute coverage is low.** Even the single best model+prompt combination (`qwen2.5-coder:7b-instruct` × `autogrep_default`) only produced a rule that passed real Semgrep validation on 10 of the 40 pilot cases (25%) -- the highest coverage anywhere in the whole 8-model x 2-prompt grid was `DeepHat/DeepHat-V1-7B` x `design_v1` at 18/40 (45%), and most model/prompt combinations landed well below that. This holds even after three retries per case with real error feedback from Semgrep. This is not a pipeline defect (every fix in Sections 12.4-12.6 is already reflected in these numbers) -- it is itself a headline-level result: on this pilot, most patch-to-rule generation attempts, across every open-weight model tested, do not end in a working rule at all. The PDS/VGR/FPR/MCC numbers above are all computed only over the subset of cases where a rule was successfully generated, so they describe "how good is the rule, given that one was produced" -- a separate and at least equally important question from "how often is one produced at all." Phase 7's analysis should report End-to-End Successful Rule Rate / coverage as a co-headline metric alongside MCC, not as a secondary detail, so this low-coverage result cannot be read past.

## 12.7 Shared repository cache: fixing a real storage/time cost before scaling to Phase 4/5

Measuring `results/runs_pilot_screening/` directly (`du -sh`) found it was 121GB, of which 120GB was git repository clones -- and every one of the 16 model x prompt run directories held its own full, independent clone of the same 42 repositories (7.5GB each, exactly 16 x 7.5GB = 120GB). `run_model_on_cases()`/`run_model()` (`pipeline/run_generation.py`) each pointed `repos_cache_dir` at a path under their own `run_dir`, so nothing was ever shared across models -- the identical repository history was downloaded and stored 16 separate times. Left unfixed, Phase 5's 300-case x 8-model primary benchmark (one locked prompt, so 8 run directories instead of 16, but ~7.5x more repositories) was projected at roughly 300-500GB for no benefit over a shared-once design's estimated 50-70GB.

The naive fix -- just point every run's `repos_cache_dir` at one shared folder -- would have reintroduced a real correctness bug, not just been a missed optimization. `rule_validator.py` calls `repo.git.checkout(parent_commit)` then `repo.git.checkout(patch_info.commit_id)` directly against whatever path `GitManager.prepare_repo()` returns, repeatedly, once per case. Since Section 12.4 already parallelized model execution across GPU hosts (concurrent threads), two models processing different cases that happen to reference the same repository at the same moment would race on that shared working tree -- one model's checkout could silently corrupt what another model was mid-validation against, producing wrong results rather than an obvious error.

**Fix implemented**: `autogrep/config.py` gained an optional `shared_repos_cache_dir` field (`None` preserves the original single-clone-per-run behavior, used unchanged by `pipeline/tests/`). When set, `GitManager.prepare_repo()` (`autogrep/git_manager.py`) now clones each repository's full history exactly once into that shared location (guarded by a per-repo `threading.Lock`, keyed by sanitized repo path, so concurrent threads requesting the same new repo for the first time can't race on "does the clone exist yet"), then creates a lightweight `git worktree` for the calling run under its own `repos_cache_dir` (`git worktree add --detach <path> <commit>`) -- a physically separate working directory that shares the shared clone's object database (the expensive part) but is fully independent for checkout/reset purposes. `reset_repo()` needed no changes (`git reset --hard` / `git clean -fd` work identically on a worktree). `cleanup_repo()` was changed to call `git worktree remove --force` instead of a raw `shutil.rmtree`, since rmtree-ing a worktree directly leaves a stale admin entry in the shared clone's `.git/worktrees/` metadata that would break a future `git worktree add` at the same path. `pipeline/gptlab_config.py` and both `run_generation.py` orchestration functions were updated to pass `shared_repos_cache_dir=results_root / "shared_cache" / "repos"` -- shared across every model/prompt run under the same results root.

**Verification before trusting it for real work** (per the project's established pattern of checking infrastructure changes against real behavior rather than code-reading alone): no two of the 40 pilot cases happen to share a repository, so the exact race condition couldn't be reproduced with real pilot data -- instead it was tested directly against `GitManager` with a small public test repository (`octocat/Hello-World`, not part of the study), simulating the real failure mode:
- 3 threads calling `prepare_repo()` concurrently for the *same* repository, through the *same* shared cache: all 3 succeeded, all 3 got distinct, independently-valid worktree paths, and the shared clone was created exactly once (confirmed by directory count), not once per thread.
- Checked out a *different commit* (detached HEAD, matching exactly how `rule_validator.py` uses this -- never a branch name) in one worktree while reading another worktree of the same repository: the second worktree's content was completely unaffected -- the specific race this fix needed to avoid reintroducing did not occur.
- `reset_repo()` on a worktree correctly removed a deliberately-added stray untracked file.
- `cleanup_repo()` on a worktree correctly used `git worktree remove` and left no stale entry in `git worktree list` for the shared clone, confirmed by inspecting the list before and after.
- All 5 existing tests in `pipeline/tests/` still pass unchanged, confirming the legacy (non-shared) code path used there is untouched.

Not yet done: an end-to-end live re-run of a real pilot case through the new shared-cache path (would need a real GPT-Lab API call; the `GitManager`-level verification above directly covers the exact mechanism that changed, so this was judged sufficient before relying on the fix for Phase 4/5, but a live smoke test is still worth doing once Phase 4 curation actually starts).

## 12.8 Phase 4 begins: 375-candidate final batch selected, then a real clone-hang bug found and fixed live

With the pilot's model/prompt selection locked, Phase 4 (the 300-case final dataset, Section 29) started. The expensive one-time infrastructure from Phase 2 turned out to already cover most of Section 8 Steps 1-2 for the final set too: MoreFixes v4 was already fully imported, language-filtered, and deduplicated into `data/morefixes_v4/candidates_deduplicated.csv` (15,585 eligible candidates -- Python 5,592 / JavaScript 4,305 / Java 3,949 / TypeScript 2,465), and only 96 of those were ever touched for the pilot's working batch. A new `pipeline/select_final_batch.py`, adapted from `select_pilot_batch.py`, selected 375 new candidates (125 each for Python, Java, and a combined JavaScript+TypeScript group -- matching Section 6.1's final-set language grouping, unlike the pilot's deliberate 10+10 JS/TS split from Section 6.0.1), explicitly excluding all 96 pilot-batch candidates so the final set stays genuinely held-out. 125 per group was chosen by applying the pilot's own observed Step-3/4 survival rate (77/96 selected, ~80%) to the 100-per-group target: 125 x 0.80 ~= 100. Every group hit its full target with substantial pool remaining (687-910 eligible per group after exclusions), confirming 15,489 untouched candidates were more than enough headroom without needing to loosen any selection criterion.

Section 8 Step 3 (real repo clone + commit checkout + diff extraction) started next via a new `pipeline/curate_step3_repo_states_final.py` (same logic as the pilot's Step 3 script, plus a missing patch-file-extraction step the final batch needed and the pilot's didn't, since the pilot's 96 patch files had already been extracted by hand previously). The first 6 candidates completed in the low tens of seconds each. The 7th, `liferay/liferay-portal`, did not: it sat for 45+ minutes with the clone directory frozen at 6.6GB and the process showing 0% CPU -- a genuine hang, not a slow-but-progressing large clone, confirmed by two `du -sh` checks 15 seconds apart showing byte-identical size.

Root cause: `GitManager._clone_or_fetch()` called GitPython's `Repo.clone_from()`, which has no timeout parameter at all -- the exact same category of gap as the earlier missing OpenAI-client timeout (`Config.request_timeout_seconds`, Section 12.4), just for git network operations instead of LLM API calls, and never caught before because no prior run had hit a repository large or flaky enough to stall.

**First attempt at a fix, and a second bug found in the process of fixing the first**: killed the stalled Python process and added `GIT_HTTP_LOW_SPEED_LIMIT`/`GIT_HTTP_LOW_SPEED_TIME` environment variables to `GitManager.__init__()` (git's own native mechanism for aborting a transfer that drops below a throughput threshold for a sustained period) and restarted. The restart's own logging showed it resuming correctly, but a `ps aux` check turned up something unexpected: the *original* `git clone`/`git-remote-https` subprocess pair (PIDs from the first attempt) was **still running**, orphaned, 45+ minutes after the Python parent that spawned it had been killed -- `kill -9` on the parent does not touch children it already spawned. This meant two separate clones were now racing into the same target directory at once. Killing only the immediately-named PID after an interrupt, without also killing the process tree it spawned, is a real operational mistake worth remembering, not just a one-off cleanup annoyance -- documented here so it isn't repeated.

**Real fix**: rewrote `GitManager._clone_or_fetch()`/new `_run_clone()` to shell out to `git clone` directly via `subprocess.Popen(..., start_new_session=True)` instead of GitPython's `clone_from()`, so it runs in its own process group; a `CLONE_TIMEOUT_SECONDS = 300` hard wall-clock cap (chosen deliberately over a shallow/depth-limited clone, which isn't safe here -- Step 3 checks out arbitrary historical commits by hash, which a shallow clone may not contain) is enforced via `proc.communicate(timeout=...)`, and on `TimeoutExpired` the **whole process group** is killed with `os.killpg(os.getpgid(proc.pid), signal.SIGKILL)` -- not just the direct child -- specifically so this can never again leave an orphaned `git-remote-https` running independently. A timed-out or failed clone raises `git.exc.GitCommandError`, so `prepare_repo()`'s existing caller-side handling treats it exactly like an inaccessible repository (excluded and logged, not retried forever) with no changes needed there.

**Verified directly before trusting it**, same pattern as every other reliability fix on this project: set `CLONE_TIMEOUT_SECONDS = 5` temporarily and re-ran the clone against the actual repository that had hung (`liferay/liferay-portal`) -- correctly raised `TimeoutExpired` at 5.0 seconds, and a `ps aux` check immediately after confirmed zero orphaned processes remained. All 5 existing tests still pass. Restarted Step 3 for real (300s timeout) with both this fix and the earlier `GIT_HTTP_LOW_SPEED_*` env vars in place.

**Step 3 finished clean**: all 375 candidates processed, no further hangs. 300 `ok` (exactly the 80% survival rate the 125-per-group oversampling was built around), 35 `excluded` (inaccessible repo, missing file at one revision, etc.), 40 `flagged_for_review` (merge commits, set aside rather than guessed, per Section 8 Step 3's own stated policy). By group among the 300 survivors: Python 98, Java 96, JavaScript+TypeScript 106 -- already close to the 100-per-group final target before Step 4 even ran, though since the 80% figure this oversampling used was originally the pilot's *combined* Step-3-plus-Step-4 yield, Step 4 was expected to cause some further attrition on top of this 300, not zero.

### 12.9 Step 4 (advisory verification) for the final batch, and a second real bug found reprocessing the results

`curate_step4_fetch_advisories_final.py` / `curate_step4b_nvd_fallback_final.py` (adapted from the pilot's Step 4 scripts the same way Step 3 was, plus resume support the pilot's version didn't need at 300 candidates' scale) ran cleanly against all 300 Step-3 survivors: 207 confirmed via a GitHub-reviewed advisory, all remaining 35 confirmed via the NVD fallback (100% resolution -- every one of the 300 candidates now has independently-confirmed, real external evidence, not just MoreFixes' own internal classification), 0 flagged refactor-only.

The CWE-disagreement flag came back suspiciously clean at first (0 of 300) -- worth being skeptical of a too-clean result rather than taking it at face value, which is exactly what surfaced the actual problem. Checked whether `github_cwes` was even getting populated at all: it was empty for 299 of 300 cases, which explained the 0 -- the flag can only fire when *both* sides are non-empty, so an always-empty side makes it structurally unable to ever trigger, independent of whether the underlying data agrees or not.

Root cause, confirmed directly against a real API response (`gh api "advisories?cve_id=CVE-2025-58753"`) rather than assumed from documentation: GitHub's advisories API nests CWEs as `"cwes": [{"cwe_id": "CWE-552", "name": "..."}, ...]` -- a list of objects -- not the flat `"cwe_ids": [...]` string list both `curate_step4_fetch_advisories.py` (the pilot's original) and its copy for the final batch were reading. That key doesn't exist in the real response at all, so `a.get("cwe_ids", []) or []` silently evaluated to `[]` on every single advisory, for both scripts, the entire time -- this bug predates today and was already latent in the pilot's own Step 4 results, just never noticed since the flag it broke is a soft "worth a closer look" signal (Section 8 Step 4), not a hard inclusion/exclusion gate, so it never silently corrupted which cases made it into the curated set.

Since `fetch_advisory()` already saves each advisory's complete raw API response (not just the fields it uses) into the results JSON, no new GitHub API calls were needed to fix this -- reprocessed the already-cached raw data directly, correcting `github_cwes`/`cwe_overlap`/`cwe_disagreement_flag` for all 300 cases in place. Corrected `github_cwes` for 254 of 300 (up from empty). Real picture once fixed: 253 cases have a CWE on both the MoreFixes and GitHub side, 234 agree, **19 genuinely disagree**. Spot-checked all 19 by eye: every disagreement is between closely-related or hierarchically-nested CWE categories (e.g. CWE-399 "Resource Management Errors" vs. its own more specific child CWE-400 "Uncontrolled Resource Consumption"; CWE-264, a broad/deprecated access-control category, against a more specific child like CWE-287/400) -- consistent with CWE's own known multi-label, hierarchical taxonomy rather than a sign of a wrong CVE-to-commit mapping (nothing resembling an alarming category-level mismatch, e.g. an injection CWE against an unrelated auth CWE, appeared anywhere in the 19). Fixed the same field-name bug in the original pilot script too, for correctness of any future reuse, even though the pilot's own already-frozen manifest isn't being redone over a soft heuristic flag that was never a hard gate.

### 12.10 Step 5 (context extraction) for the final set: automating target-function location, and verifying it before trusting it

The pilot's Step 5 scripts (`extract_context_python.py`/`_java.py`/`_js_ts.py`) located each case's vulnerable/patched function via a hand-curated `case_id -> (function_name, class_name, ...)` table -- workable for 40 cases, not for 300+. The actual task ("which function contains the lines this diff changed") is mechanical, not a judgment call, so built `pipeline/auto_locate_target.py`: parses `patch.diff`'s hunk headers to get changed-line ranges in both revisions, then finds the smallest enclosing function/method (and its class, if any) whose span contains those lines -- exact via the `ast` module for Python, via a general brace-block enumerator (reusing/extending the pilot's own literal-and-comment-aware brace matcher) for Java/JS/TS, since no parser library is available for those.

**Verification methodology, agreed before writing any of the 300-case logic**: re-derive all 40 pilot cases' targets automatically and compare against the pilot's own hand-verified answers (`benchmark/model_context/CASE-*.json`) -- real, independently-known-correct ground truth, not a synthetic test. `verify_auto_locate_against_pilot.py` runs this comparison and was re-run after every fix below. Started at 11/40 exact match; ended at 25/40, with the rest falling into well-understood, non-mysterious categories (documented in the tool's own next-turn report to the user), not silent failures.

**Real bugs found and fixed via this verification, each confirmed against actual pilot case data before being trusted**, roughly in the order found:
- Trusting only a diff's FIRST hunk picked module-level noise (an import change) over the real fix, which sat in a later hunk (CASE-0002) -- fixed by trying every hunk, weighted by its own changed-line count, and picking whichever function accumulates the most support.
- A single hunk can itself span two unrelated regions separated by unchanged context (CASE-0002 again: one hunk touched both a class docstring, not inside any function, AND a full rewrite of `execute()`/`_safe_eval()`/etc., very much inside functions) -- fixed by splitting hunks into contiguous changed-line RUNS rather than treating each `@@ ... @@` hunk as one atomic unit.
- Allman-style braces (the `{` on its own line after the signature, common in older Java) meant the extracted text started at the brace, silently dropping the entire signature above it (CASE-0019).
- A trailing `}`/`;`/`{` immediately followed by a newline still counted as "on the same line" for line-index purposes, so the blank/comment-skipping loop that was supposed to walk past a preceding Javadoc block never even started (CASE-0014 and several others) -- root-caused to an off-by-one in how a character offset landing exactly on a newline was mapped back to a line number.
- The "is this a bare/static initializer block" check (`\bstatic\s*$`) never actually matched, because `opening_context` always includes the block's own trailing `{` and the regex only tolerated trailing whitespace, not a literal brace character -- found on a real Java security denylist built entirely inside a `static { ... }` block (jackson-databind's `SubTypeValidator`), the same construct as the pilot's own hand-special-cased CASE-0011.
- A class/interface/enum declaration's own brace could satisfy the method-shaped `"(...)"` check purely because of an annotation on it (`@Component("cubeMgmtService")\npublic class CubeService ... {`), so the entire class got extracted as if it were "the vulnerable function" (CASE-0016) -- fixed by making the class-like and method-like classifiers explicitly mutually exclusive.
- Line-based (not character-precise) extraction pulled in trailing same-line content belonging to an OUTER statement, e.g. the `);` closing a `.set('key', function() {...})` call (CASE-0029) -- fixed by switching the whole brace-block scanner to track exact character offsets throughout, extracting `source[start:end]` rather than whole lines.
- A pure insertion (only `+` lines, no `-` lines) can land exactly on the blank line between two functions' bodies, which neither function's span technically includes (`frappe/lms`'s `CourseChapter.on_update()`) -- fixed with a deliberately narrow two-pass retry: try every hunk at its exact line first, and ONLY if that finds nothing at all across every hunk, retry with a +/-1 line tolerance. A first attempt at this applied the +/-1 tolerance unconditionally on any single failed line and it backfired, verified: it regressed two previously-correct pilot matches (CASE-0003, CASE-0015) by letting an imprecise nearby match outvote a different hunk's exact, correct one. Restricting the retry to a true last resort (nothing at all resolved) fixed both without losing the fix it was added for.

**Applied to the real 375-candidate final batch** (`extract_context_final.py`, reusing `auto_locate_target.py` directly): of the 300 cases that survived Steps 3-4, 223 resolved with a single clearly-favored answer ("auto"), 41 resolved but with a close runner-up candidate (flagged "auto_low_confidence" but still written and usable), and 36 found no enclosing function at all. Triaged those 36 rather than force-fitting them: 2 don't even parse as modern Python (one is Cython mislabeled "python" by MoreFixes, using `cdef`/`ctypedef`/`DEF` syntax; one uses Python-2-only leading-zero octal integer literals, e.g. `0755`), 3 are version-string-only bumps (`__version__ = "0.12.19"` -> `"0.12.20"`) matching Section 7.2's own exclusion criteria directly, and 31 are genuinely module-level changes (import lines, config constants, a bare field-modifier change) -- the same category as the pilot's own hand-special-cased CASE-0010/0026/0034, where even human judgment differed case to case (CASE-0010's answer was the whole file; CASE-0026's was just the one changed statement).

Per-language survivor counts after this landed short of the 100-per-group target (Python 84, Java 90, JS+TS 90), because 36 candidates were excluded rather than forced. Rather than hand-resolve those 36, pulled a small top-up batch from the same eligible pool (`select_topup_batch.py`, excluding all 471 candidates already tried across the pilot and the original 375-candidate batch): 25 Python, 16 Java, 16 JS+TS, oversampled at the same ~80% survival rate already observed twice now. Ran it through the identical Steps 3/4/5 (path-substituted copies of the same scripts -- `..._topup.py`), yielding 39 more usable cases (30 confident, 9 low-confidence, 6 more excluded for the same reasons as before) at the same ~87% success rate.

**Final combined total: 303 usable cases -- Python 103, Java 101, JavaScript+TypeScript 99** -- matching Section 6.1's 100-per-language target closely; Section 6.1 explicitly treats this as a target rather than a hard requirement ("preserve all verified cases and report macro-averaged results" when exact parity isn't achievable). The user asked for the JS+TS shortfall to be closed exactly anyway; a tiny third selection (3 candidates, `select_topup2_batch.py`) both survived, landing JS+TS at 101 (one over rather than exactly 100 -- left as-is rather than discarding a genuinely good, verified case just to round a number).

### 12.11 A real bug found reading the difficulty-classification output, not looking for one

Before starting Step 6, re-read the pilot's own `classify_difficulty.py` closely enough to actually build its final-set equivalent, and caught something the earlier "303 usable cases" count had not surfaced: two of the pilot's five recorded fields -- `pattern_or_taint` and `structural_or_context_heavy` -- are not mechanically derivable at all. The pilot script's own docstring says they came "from this session's direct, hands-on construction of every case's Section 9 ground-truth bundle" -- i.e. they were a byproduct of deeply engaging with each case while writing its test-variant transformations, not something a script computed. A third field, `supported_status` (semgrep_representability), turned out to be the same category -- assessed by hand during the pilot's Step 4, never captured for the final set's Step 4 either. Flagged this to the user before writing anything rather than fabricate 305 shallow judgments; agreed to compute only the genuinely mechanical fields now (language, CWE, diff stats, function size, `auto_locate_confidence`) and defer all three judgment fields to Section 9, when the deep per-case reading happens anyway -- doing it once, not twice. `classify_difficulty_final.py` implements this reduced scope explicitly, with a `classification_pending_reason` field on every record rather than silently omitting the three fields.

Running it surfaced a real, unrelated data problem while sanity-checking the output: the largest recorded `vulnerable_function` was 1214 lines (`agenticmail`'s `storage-routes.ts`) -- absurd for what should be one function. Traced it: `auto_locate_target.py`'s brace-block scanner treated backtick template literals exactly like plain quoted strings, with no handling for `${...}` interpolations containing real code (including their own braces, e.g. an inline object literal or arrow function). A `${...}` interpolation's brace could desynchronize the depth counter from the rest of the file, matching a much-later, unrelated closing brace -- and the case had been marked "auto" (highest confidence) despite being wrong, since nothing in the confidence signal was sensitive to this failure mode. Fixed by porting the same mode-stack approach already proven in the pilot's own `extract_context_js_ts.py` (`extract_block_by_anchor`) into the shared scanner -- braces inside a `${...}` interpolation now behave as ordinary code for nested-block purposes, and the "}" that specifically ends the interpolation is identified by mode, not depth, matching that already-validated implementation's exact behavior (including its accepted limitation on further-nested nested nested interpolations, which real cases haven't hit). Re-verified against the pilot afterward: still 25/40, no regression.

That fix alone didn't change `agenticmail`'s result, though -- re-checking it directly found the true cause was unrelated to template literals for this specific file (root cause not tracked down further; judged not worth continued open-ended debugging for one file). Rather than keep chasing individual parsing edge cases, added a general, bounded safety net instead: any extracted "function" over 150 lines is now routed to manual review regardless of whether the extraction is technically correct, since a 150+ line blob isn't useful model context either way -- confirmed this is the right framing by checking two of the other flagged oversized cases (`crypto-js`, `npm`-cli) and finding both were genuinely large, legitimate whole-file IIFE wrappers, not bugs, yet equally unhelpful as "the vulnerable function."

Re-running Step 5 with both fixes landed on an unchanged combined case count at first, which was itself the next bug: the script never cleared its output directory between runs, so `agenticmail`'s known-bad file (and others like it) were still sitting in `model_context_final/` from before the size gate existed, silently masking the fix's real effect. Fixed by clearing `*.json` from the output directory at the start of each run, matching the principle that a run's output should exactly reflect that run's own decisions, not accumulate stale leftovers from earlier ones. With both fixes actually taking effect, the true post-fix count was Python 99, Java 92, JS+TS 91 (282 total) -- a real shortfall the stale-file bug had been hiding. Pulled a third top-up batch (`select_topup3_batch.py`, 29 candidates: 3 Python, 12 Java, 14 JS/TS) to cover it, through the identical Steps 3-5 chain -- one candidate (`liferay-portal` again, the same huge repo from Section 12.8's clone-hang bug) took the full 300-second timeout before failing, exactly as designed this time, rather than hanging.

**Final Phase 4 dataset: 303 usable cases -- Python 100, Java 101, JavaScript+TypeScript 102** (78 JS + 24 TS), all at or above the 100-per-language target, verified via three independent checks: zero cases over the 150-line size gate, zero duplicate case IDs across the four selection batches, and no regression against the pilot's 40 known-correct answers (still 25/40 exact match) at any point during this round of fixes.

Step 6 (`classify_difficulty_final.py`) then ran cleanly across all 303 cases -- mechanical fields only (language, CWE, diff stats, function size, `auto_locate_confidence`), with `pattern_or_taint`/`structural_or_context_heavy`/`supported_status` explicitly deferred to Section 9 per Section 12.10's decision. ### 12.13 Starting Section 9, finding three more `auto_locate_target.py` bugs on the FROZEN final set, and re-freezing

Began Section 9 (the six-sample ground-truth bundle) on the frozen 302-case final set, following the pilot's exact methodology: hand-written, deterministic per-case transformation scripts (`pipeline/section9_final/build_bundle_caseNNNN.py`), never LLM-generated, per Section 9.2's "do not allow an evaluated model to certify its own test variants" -- confirmed by re-reading Section 9.2 directly before starting, not from memory. `CASE-0041` (MaxKB, CSV/Excel formula injection, CWE-1236) completed cleanly: 4 variants written, all syntax-verified (`py_compile`), logged to a new `benchmark/transformation_manifest_final.jsonl`.

`CASE-0042` (copyparty, a `shr_files` access-control bypass, CWE-552/862) immediately surfaced a real problem: its `changed_function` was `_ls_nope`, a 4-line stub that raises an exception -- completely unrelated to the actual vulnerability (missing `canonical`/`dcanonical` method-swap wiring for restricted shares). Rather than special-case one file, wrote a diagnostic (comparing each case's extracted function's line range against the diff's actual deleted-line positions, parsed precisely from the raw patch rather than hunk-header ranges, which include padding context that produces false overlaps) across all 302 final cases. Found 14 candidates; manually confirmed two: `CASE-0042` (above) and `CASE-0221` (`is-my-json-valid`, CVE-2016-2537), where `changed_function` was literally `"?/g"` -- garbage sliced out of the middle of a regex literal.

**Root cause 1 (`CASE-0042`)**: `_best_across_hunks()` correctly weights candidate functions by total changed-line count, but a pure-insertion hunk's `old_line` target is a GAP position between two old-file lines, not real content. copyparty's fix inserted two new methods immediately before the existing `_ls_nope()`; the gap position numerically coincided with `_ls_nope`'s own def line, so the exact `node.lineno <= target_line <= node.end_lineno` check falsely attributed the insertion to that unrelated following function. Fixed by threading a `has_deletion`/`has_insertion` flag through `HunkTarget` and requiring, for a side whose line number is a gap position (no deletion on the old side / no insertion on the new side), the target line to fall STRICTLY after the candidate's own signature line -- a genuine "first line of this function's body" insertion always lands at `signature_line + 1` or later, so this can only reject the boundary false-positive, never a real match.

**Root cause 2 (`CASE-0221`, and separately `CASE-0176`)**: the brace-block scanner had zero awareness of JS/TS regex literals -- a `{n,m}` quantifier inside an EARLIER regex in the same file (`formats.js` has several, e.g. `{6,14}`) was read as a real code brace, desynchronizing depth-tracking for the rest of the file and producing garbage extracted "functions" starting mid-regex. Fixed with a heuristic regex-literal detector (the previous non-whitespace character is one that can only precede a new expression -- `=([{,!&|?:;` or newline/start-of-file, distinguishing a regex literal's `/` from a division operator's) that scans and skips the whole literal as a unit once detected, mirroring the existing backtick-template-literal mode-stack fix (Section 12.11) rather than tracking it character-by-character.

**A third bug found DURING verification of the first fix**: re-running the pilot's 40-case regression check after the boundary-sensitivity fix initially showed one NEW final-set case gone wrong, `CASE-0093` (alfio, CSV formula injection again) -- its extraction landed mid try-with-resources-declaration (`CSVWriter writer = new CSVWriter(...)) {`, missing the `try (` prefix and control-flow classification that should have excluded it). ### 12.18 Filling the three deferred classification fields for all 300 cases

Section 9's bundles were complete (300 cases, 1,200 manifest rows, verifier clean), so the three fields deliberately left null since Section 12.10 -- `pattern_or_taint`, `context_complexity` (the pilot's `structural_or_context_heavy`) and `semgrep_representability` -- were filled for every case. Same method as the pilot (Section 12.10/`classify_difficulty.py`): a hand-judged table, one line of rationale per case, made from what building each case's bundle showed about its mechanism, not derived by a script. The judgements live in `benchmark/labels_final.json`, keyed by the ORIGINAL pipeline case id so they survive case-id shifts, with the rubric in the file's `_meta`; `freeze_manifest_final.py` now reads it, so a re-freeze reproduces the labels instead of erasing them.

**Rubric (design doc Section 7.3).** *Supported*: the vulnerable code has a matchable shape inside the function itself (dangerous call/API, missing-check or missing-annotation idiom, tainted flow to a sink, hard-coded secret, missing entry in a literal security list -- matching the pilot's precedent for its denylist case). *Partially supported*: Semgrep can observe part of the mechanism but important context is unavailable -- notably a locally matchable faulty expression or statement order whose wrongness is semantic (wrong operand, constant or argument, inverted comparison), or a sink/source/semantics outside the function, or framework/runtime behaviour that decides the harm. *Unsupported*: the vulnerable/patched difference is not a code-shape property (timing side channels, cryptographic parameter quality, data remanence, log volume, file-system or runtime behaviour, parser differentials, cross-function bookkeeping, business or authorization logic spread over several steps). The rubric was made uniform partway through: after the first chunks I noticed logic bugs with an observable local fault were being split between "supported" and "unsupported" by feel, so they were all moved to "partially supported" and nine earlier calls were revised for consistency (plus three statement-order cases).

### 12.20 Post-Section-9 pipeline test on final cases (no API key): five defects found, three fixed

Purpose: before spending GPU time on Phase 5, exercise the whole benchmark path on FINAL-set cases (the pipeline had only ever run on the pilot's 40). Done without a model or API key, in three parts; the scripts are kept in `pipeline/tests/` (`run_gold_rules_final.py`, `run_fake_llm_final.py`, `gold_rules_final/`).

**(1) Static sweeps over all 300 cases.** All 300 cases load through `case_loader.load_case`, and both prompt variants build for all of them (default prompt: median ~3.8k chars, max ~9.5k = ~2.4k tokens; `design_v1` reaches ~64k chars, ~16k tokens, for at least one case -- a context-window risk for 7B models if that variant is ever used). `vulnerable_lines` is in range for every case. **Semgrep scans all 1,800 sample files (300 cases x the 6 bundle samples) with zero parse errors and zero skipped files**, using a never-matching rule so any `errors` entry could only be a parse failure -- direct evidence for inclusion criterion 7.1 ("the affected file parses"), and important because the scorer silently treats a target-file parse failure as "no finding".

**(2) Scorer test with hand-written gold rules** (7 cases across all four languages, plus match-nothing and match-everything invariant rules per case). The invariants hold exactly (match-nothing: FN on the three vulnerable samples, TN elsewhere; match-everything: TP on vulnerable, FP elsewhere). Three gold rules score IDEAL (TP on original+both vulnerable variants, TN on patched+safe+benign): CASE-0079, 0105, 0181. The others fail because of the rule, not the bundle: CASE-0078/0238/0342 have a benign look-alike that is syntactically identical to the vulnerable code (0238: `Papaparse.unparse({...})` with program-generated rows; 0342: `new Yaml()` on a bundled resource), so **no purely syntactic rule can score TN on those benign samples** -- a ceiling on the benign-discrimination metric for such cases, to be kept in mind when interpreting BSDR.

**(3) Full generation path with a fake model** (real `run_model_on_cases`, real Autogrep retry/validation against real git checkouts, real bundle scorer; canned model replies). Produced the expected 10 generation records and 42 sample records; raw and autogrep conditions diverge exactly as designed (CASE-0341: raw keeps the useless first answer, Autogrep retried three times and failed); location correctness is recorded on final cases.

**Defects found.** *Fixed:* (a) `run_generation._load_frozen_manifest_index` read only the pilot manifest, so `vulnerable_lines` was empty for every final case and finding-location correctness (design Section 9.3) would silently never have been measured on the final benchmark -- now reads both manifests. (b) `--results-dir` was used as a RELATIVE path, but `git worktree add` runs inside the shared clone, so the per-run worktree was created INSIDE the cached repository (the test polluted four cached clones under `data/`; cleaned up with `git worktree remove` and each clone verified back to a clean status) -- `run_model_on_cases` now resolves it to an absolute path. (c) CASE-0078's hand-curated fix commit lives on a pull-request branch that a normal clone does not contain, so Autogrep's validation would have failed with "commit not found" -- `GitManager` now falls back to `git fetch origin <sha>` (GitHub serves any reachable commit); verified live from a fresh clone (note GitPython raises `ValueError`, not `BadName`, for an unresolved full SHA). *Noted, not changed:* (d) Autogrep's schema check requires a top-level `pattern:`; any rule using `patterns:`, `pattern-either:` or `pattern-not:` is rejected in BOTH conditions, which limits what any model can express (e.g. it can never exclude a benign look-alike with `pattern-not`); this is pinned Autogrep behaviour, but the pilot's pipeline finding stands and should be stated as a limitation. (e) The Autogrep condition validates against git checkouts of the real repository: the 300 cases span 258 repositories and the local clones total ~48 GB (largest 1.7 GB, apache/camel), 296 of 300 cases have both commits in the local clones (0238, 0339, 0340 have no local clone and would be cloned fresh; 0078 needs the fallback above). The validator only reads the same single file the case already stores as `vulnerable_source`/`patched_source`, so a standalone-file validation path would remove the clone dependency; that is a Phase 5 design decision, not made here.

**Addendum -- first real-model attempt failed on authentication, and the pipeline hid it.** The first real-model smoke run (8 final cases, `qwen2.5-coder:7b-instruct`) produced 8 blank "autogrep" records, no raw captures, no sample results and no attempts. Diagnosis: no model response was ever received (`raw/`, `raw_retries/`, `generated_rules/` all empty; the whole run took ~100 s, mostly repo cloning), and an unauthenticated request to the same host returns `401 "Invalid or Missing Bearer Token"` while the host is reachable from this machine -- so the token that reached the process was rejected. The pipeline made this look like ordinary failures: the API error was swallowed inside `generate_rule()`, the record's `validation_error` stayed empty, and Autogrep's own cache marked all 8 patches "processed", so re-running into the same results directory would have silently skipped them (the same trap as Section 12.5). Fixed: (1) `run_generation.py` now runs a **preflight authentication check** against every host it will use and exits with a clear message before doing anything, verified with a deliberately wrong key (exit 1, no result folder created); (2) when no attempt reaches the model the record now keeps the LLM client's `last_error`; (3) `Open Models/models.py` exits non-zero on a non-200 response; (4) `pipeline/tests/run_final_smoke.sh` uses `pipefail`, prompts for the key with hidden input (never written to disk) and writes to a fresh timestamped results directory. The failed run is kept, without its caches, as `results/runs_final_realsmoke_FAILED_401_bad_key/`. Lesson for Phase 5: a bad or expired key mid-run must not be able to produce a "complete" run of blank failures.

### 12.30 A real bug found auditing inputs before Phase 7 analysis: `reconstruct_attempt_trail()` never updated for the clone-free refactor

While checking the raw `validation_error` strings before building the Phase 7 failure-reason breakdown (Section 16.1's correctness levels need to distinguish failure types, not just pass/fail), found that **"repo not available for validation" is by far the single most common error string** in the Phase 5 results -- far more common than any real Semgrep parse error or discrimination miss.

**Root cause**: `reconstruct_attempt_trail()` (added in Section 12.4, a diagnostic-only re-evaluation of every captured attempt, independent of Autogrep's own retry loop) still gated its per-attempt re-validation on `repo_path.exists()`. That check was correct before Section 12.24's clone-free refactor -- for curated cases, `git_manager.prepare_repo()` now deliberately returns a synthetic marker path that never exists on disk, since no clone is needed. `reconstruct_attempt_trail()` was never updated to know this, so for every curated case it saw `repo_path.exists() == False` and concluded "can't validate," discarding the REAL per-attempt outcome.

**What this did NOT affect, confirmed by reading the code (not by re-running anything -- the platform's Bash tool was down for part of this investigation, so verification proceeded by direct source inspection where possible)**: `autogrep_gen.semgrep_valid` -- the actual pass/fail boolean already reported in Section 12.29's coverage snapshot -- is set directly from Autogrep's own real `process_patch()` result (`autogrep_rule is not None`), which internally uses the already-correct clone-free `rule_validator.validate_rule()`. `reconstruct_attempt_trail()`'s output is never read for that field. **The coverage numbers already reported stand.**

**What it DID affect**: the `attempt_trail` diagnostic list (why each individual retry failed) and, for total-failure cases specifically, the top-level `validation_error` message (`autogrep_gen.validation_error = attempt_trail[-1].get("error")` when every attempt failed) -- both became unreliable for curated cases specifically, systematically over-reporting "repo not available" instead of the real reason. This matters for the Phase 7 failure-taxonomy breakdown (checklist item #15) but not for any pass/fail count already computed.

**Fixed**: the `repo_path.exists()` guard now only applies when `patch_info.case_id is None` (the raw-.patch-file flow, where it's still a meaningful check) -- for curated cases, `validate_rule()` is called directly, since it already knows to read the standalone case files. Once Bash access returned, verified precisely: all 1,746 occurrences of the top-level `validation_error == "repo not available for validation"` are in the `autogrep` condition (0 in `raw`, which never calls this function), and all 1,746 have `semgrep_valid == False` -- confirming the bug never produced a wrong pass, only a wrong failure-reason string. 5,769 of 6,371 individual `attempt_trail` entries (90.6%) carried the corrupted diagnostic text. Existing `generation_log.jsonl` files are NOT retroactively edited -- kept as an accurate record of what happened; this note explains the affected field. Fix applies going forward (the Section 13.4 stability experiment will get correct diagnostic detail).

### 12.56 Section 22 (formal statistical analysis) built and run -- a crucial honesty correction on the C4 narrative

Scoped first (`Research_Log/Section22_Scope.md`), confirming all data already exists (primary benchmark raw/autogrep x 8 models, C2 x 8 models, C3-S/C3-E, C4-A/C4-B, all with a compatible `sample_execution_log.jsonl` schema -- `confusion_from_samples`/`mcc`/`per_case_vgr_fpr` reused directly everywhere, no duplication). One real methodology decision, documented rather than silently made: Section 22.2 says "Wilcoxon signed-rank for paired MCC," but MCC in this study has always been a POOLED statistic (no natural per-case value) -- resolved via a case-level paired bootstrap (resample cases with replacement, recompute pooled MCC per condition per resample, derive a 95% CI and two-sided bootstrap p-value on the difference) for MCC/VGR/FPR/PDS, reserving true Wilcoxon for genuinely per-case scalars (tokens/latency) and McNemar for the per-case binary ESR outcome.

Built `pipeline/stats_section22.py` (hand-rolled exact McNemar via `scipy.stats.binomtest`, hand-rolled Holm correction, the paired bootstrap, thin wrappers over `scipy.stats.friedmanchisquare`/`wilcoxon`) -- statsmodels isn't installed and both McNemar/Holm are simple enough to implement directly rather than add a new pinned dependency. **Verified every primitive against known-answer examples before trusting them on real data** (`pipeline/tests/test_stats_section22.py`): McNemar matched a textbook p-value to 4 decimal places; Holm matched a hand-computed 4-test example (one test initially written with a WRONG hand-computed expected value, caught by the code correctly enforcing Holm's monotonicity constraint -- the code was right, my test's manual arithmetic was wrong, fixed); the bootstrap correctly detected a known constant difference and correctly returned a null result for identical conditions; Friedman matched a clear pattern and correctly handled scipy's silent NaN-on-degenerate-input behavior (confirmed directly, not assumed, via a RuntimeWarning check) rather than letting a NaN propagate unflagged into a real result.

**A real bug caught during the loader build, before any numbers were trusted**: the primary benchmark's `generation_log.jsonl` has `input_tokens`/`output_tokens`/`generation_seconds` as `None` for EVERY record in both `raw` and `autogrep` conditions (confirmed by direct inspection, not assumed) -- this metadata was simply never captured during Phase 5. My first loader draft used `(g.get("input_tokens") or 0)`, which silently turned every `None` into `0`, making every case's "tokens" identical across conditions and producing a spurious Wilcoxon result (`stat=0.0, p=nan`) that looked like real output rather than a missing-data signal. Caught by checking the raw values directly rather than trusting the printed number, fixed by propagating `None` honestly so the comparison code correctly skips Wilcoxon and reports the limitation instead of fabricating a result. Confirmed C2's own token/latency fields ARE genuinely populated (not subject to the same gap) before using them.

Ran all 7 predefined comparisons (Section 22.3) on the 153 supported cases (full report: `results/section22/comparisons_1_7_report.txt`). Headline results:

1. **Qwen2.5-Coder 7B vs 32B**: not significant either way (ESR McNemar p=1.0, MCC bootstrap p=0.546) -- genuinely comparable at this task, consistent with their close MCC values throughout this whole study.
2. **Qwen2.5-Coder 7B vs DeepHat 7B**: not significant (MCC bootstrap p=0.362) -- no measurable security-fine-tuning effect detected.
3. **Small code-model family effect** (6 models, ~7-9B scale, Friedman on ESR): **omnibus IS significant** (stat=14.262, p=0.014) -- real aggregate differences exist among the family -- but **zero pairwise comparisons survive Holm correction** (best adjusted p=0.469). Honest, reportable pattern: something differs across the family, but with ESR's low base rate (1.3%-6.5%) and only 153 cases, the data can't pin down WHICH specific pair after multiple-comparison correction.
4. **Raw vs Autogrep (pipeline effect), all 8 models**: ESR shows no significant difference for any model (0/8 after Holm correction -- ESR's strict threshold means almost no case passes in either condition, leaving McNemar almost no power). **But the pooled-MCC bootstrap shows a massive, highly significant improvement for EVERY model** (all 8 at bootstrap p=0.0000, e.g. qwen7b-instruct 0.168->0.613, codegemma 7b -0.043->0.591) -- Autogrep's retry/validation loop produces a real, large, extremely consistent quality improvement across the whole sample distribution, even though it essentially never pushes a case over ESR's strict all-or-nothing bar. This is the single most robust, well-powered finding in the whole Section 22 analysis.
5. **C1 vs C2 (iterative feedback effect)**: same shape and same conclusion as #4 for all 8 models (expected, since C2 and autogrep were already known to produce near-identical MCC per model -- Implementation_Log 12.36-12.38).
6. **C2 vs C3 (role-separation effect)**: `qwen2.5-coder:32b` C2 vs C3-S -- MCC diff +0.097 in C3-S's favor, 95% CI (-0.009, +0.208), bootstrap p=0.073 -- **suggestive but NOT significant at the conventional 0.05 threshold** (the CI almost, but doesn't quite, exclude zero). `qwen2.5-coder:7b-instruct` C2 vs C3-E -- flat, diff +0.008, p=0.931, confirming the earlier "no quality gain for the smaller model" finding. **This measurably softens Implementation_Log 12.52's original framing ("C3-S WINS decisively on MCC") -- the direction is right and consistent with the role-separation story, but formally it's a trend, not a confirmed effect, at this sample size.**
7. **C3 vs C4 (heterogeneous assignment effect)**: Friedman omnibus on ESR across all 4 multi-agent configs is NOT significant (p=0.098). Since MCC (not ESR) was the metric the C4-A/C4-B narrative was actually built on (Implementation_Log 12.54-12.55), ran pairwise MCC bootstraps directly too, for all 6 pairs: **NONE reach even uncorrected significance at 0.05** -- the closest is C3-S vs C4-A (observed MCC 0.686 vs 0.552, but bootstrap raw p=0.125, Holm-adjusted 0.749). Root cause, confirmed directly rather than assumed: each condition's pooled MCC is built from a genuinely small number of accepted cases (C3-S=35, C4-B=26, C3-E=13, C4-A=11) -- case-level bootstrap resampling at this scale produces wide confidence intervals that comfortably include zero for every pairwise difference.

**This is an important, must-report correction to how the C4-A/C4-B findings (12.54-12.55) should be framed going forward**: the "number of distinct model conventions" interface-mismatch story remains a plausible, mechanism-grounded READING of the observed point estimates (0.552 to 0.686 MCC range, a real and fairly large-looking spread), and nothing about this analysis contradicts it -- but it is NOT a statistically confirmed effect at n=153 supported cases. The honest framing for the eventual paper: an observed pattern consistent with the interface-mismatch hypothesis, not distinguishable from chance at conventional significance thresholds given this sample size, flagged explicitly as an area where a larger case set (or the full 300-case set, if the multi-agent conditions were ever re-run there) would give the comparison more power.
